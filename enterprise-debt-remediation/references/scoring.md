# 评分规则

不要只看“看起来糟不糟”，要看风险、影响面、修复成本和证据强度。

## 评分维度

给每条债务至少记录以下维度：

- 严重度：对安全、数据、发布、核心业务的伤害有多大
- 影响面：会影响多少用户、多少页面、多少服务、多少环境
- 可复现性：问题是否稳定出现，还是偶发
- 可利用性：安全问题是否容易被触发或被放大
- 修复成本：S / M / L
- 证据强度：高 / 中 / 低

## 建议字段

债务台账至少包含：

- ID
- 类别
- 证据
- 影响
- 优先级
- 修复成本
- owner
- 验证方式
- 状态

`owner` 不明确时写 `TBD`，不要省略。`状态` 使用 `confirmed`、`pending-evidence`、`in-progress`、`done`。

## 分级

### P0

- 直接造成安全事故、数据损坏、权限绕过、严重故障、发布阻断、不可恢复状态
- 先修，不排队

### P1

- 影响核心链路、造成高频失败、让回滚或发布不可靠、让关键测试失效
- 尽快修，进入近期路线图

### P2

- 主要影响维护效率、扩展性、稳定体验和一致性
- 纳入短中期治理

### P3

- 主要是视觉 polish、文档完善、局部整理、非关键体验提升
- 放入低优先级池

## 评分公式

需要更稳定排序时，用这个轻量公式：

```text
score = severity + impact + exploitability + recurrence - fix_cost
```

取值：

- severity：1-5
- impact：1-5
- exploitability：0-3，仅安全和数据类问题常用
- recurrence：0-3，稳定复现或高频问题更高
- fix_cost：1-3，成本越高扣分越多

公式只用于同优先级排序，不覆盖 P0/P1 的硬门槛。

## 排序规则

1. 先排 P0，再排 P1，再排 P2，最后排 P3。
2. 同级里先排高影响、低成本、证据强的项。
3. 同级里先排能解除连锁风险的项。
4. 同级里先排会影响审计、发布、回滚、恢复能力的项。
5. 证据不够时，标记为“待验证”，不要直接当结论。

## 实用判定

- 能导致数据丢失或越权的，直接视为高优先级。
- 能让核心路径反复出错的，优先于纯视觉问题。
- 需要大改架构才能解决的，先拆成可验证的小步。
- 只靠主观审美判断的 UI 问题，优先级低于信息结构和可访问性问题。

## 路线图切法

- 立即止血：先消除安全、数据、发布风险
- 短期整改：补关键测试、补可观测性、补最差体验
- 中期重构：收边界、降耦合、统一设计系统
- 长期治理：建立门禁、规范、owner、巡检和复盘机制
